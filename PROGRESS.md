# RazeXR -> PCVR: Progress

Target: an exact 1:1 port of Team Beef's RazeXR (OpenXR VR Build engine, on
Raze) to PCVR, for a Quest 3 over Virtual Desktop (VDXR), then a separate PC
branch carrying an in-game Switch Game menu modelled on VRaze's.

Companion projects: `../QuakeQuestVR` (Quake 1, complete) and
`../Quake2VR-741` (Quake II, complete). Their `PROGRESS.md` files document the
workflow this project follows.

### Correction to the starting assumption

Upstream Raze has **no 1.7 release tag** — its tags run `1.7pre` then `1.8pre`.
`VERSIONSTR` at the base is `"1.7pre"`; DrBeef edited it to `"1.7"` in
`source/core/version.h` as part of his fork. So the `# generated by Raze 1.7`
header in both `razexr.ini` and `vraze.ini` is *his* string, inherited by
anything downstream of him. It confirms VRaze descends from RazeXR. On its own
it is **not** evidence that VRaze sits on the same engine base.

That claim is nevertheless true, established below by a stronger measurement.

## The one real architectural problem: multiview

This is the finding that shapes the whole port, and it has no analogue in either
previous project.

**RazeXR renders stereo in a single pass using `GL_OVR_multiview2`**, a mobile
extension. Concretely:

- `vrmi_openxr` declares **one** eye (`mEyeCount = 1`), so the engine runs the
  scene once
- `HWViewpointUniforms::mProjectionMatrix` became `VSMatrix[2]`
- `wadsrc/static/shaders/glsl/main.vp` ends with
  `gl_Position = ProjectionMatrix[gl_ViewID_OVR] * eyeCoordPos;`
- `gl_shader.cpp` emits `#extension GL_OVR_multiview2 : enable` and
  `layout(num_views=NUM_VIEWS) in;`
- the OpenXR swapchain image is a 2-layer texture array

**The C++ half of that is `#ifdef __MOBILE__`. The shader half is not.** On a
desktop build `NUM_VIEWS` is never defined and `gl_ViewID_OVR` is never
declared, so `main.vp` cannot compile. Their tree does not build a working
desktop renderer as it stands — exactly the Quest-to-PCVR seam pattern, and the
single largest item of real work in this port.

Two ways out, and this is the main decision needed before code (see below).

Note also: the Android build compiles the **desktop `gl` backend** with GLES
shims, not Raze's `gles` backend. `wadsrc/static/shaders_gles/` is stock and
unused by them — a red herring, and its `main.vp` still has the stock non-VR
line.

## VRaze, measured from its data

Comparing the two shipped `raze.pk3` files, line-ending-normalised:

- **3,666 lumps in RazeXR, 3,791 in VRaze**
- **Zero lumps present in RazeXR but missing from VRaze** — a strict superset
- **125 added files**
- **Of the 3,666 shared lumps, exactly 18 differ in content.** The 321 that
  differ by hash are almost all CRLF-vs-LF: RazeXR's pk3 was built on Windows,
  VRaze's on Linux

**That is the real evidence that VRaze did not rebase.** A fork moved onto a
later Raze would differ in hundreds of zscript and shader lumps, not eighteen.
So the plan holds: converting to VRaze later stays cheap, and the `.ini` header
coincidence turns out to be true for a better reason than the header.

The 18: `menudef.txt`, `language.0` (regenerated from the csv), `grpinfo.txt`
(two extra addon GRP definitions), `defbinds` x3, per-game `widescreen.def` x7,
`loadsavemenu.zs`, `blood/ui/sbar.zs`, and three Duke actor scripts.

### The 125 added files are two features, not one

1. **The switcher** — menu definitions only.
2. **Voxel weapons in hand.** Per-game `vr_weapons.def`, `vr_weapon_offsets.def`
   and `vr_weapon_animations.def` under `filter/<game>/engine/`, plus ~100
   `.kvx` voxel models under `models/weapons/<game>/`. RazeXR has none of these.

That second one is a much bigger feature than the switcher and it is worth
saying plainly: **VRaze replaced Build's flat weapon sprites with actual 3D
voxel models**, with per-weapon offset menus (`VRWeaponOffsetList` and six
per-game variants) to position them. If part of what is liked about VRaze is
"the guns look right in VR", that is this, not the switcher.

`vr_weapons.def` is ordinary Build `.def` syntax — `voxel "<path>" { tile N
scale S }` mapping tiles 30000-30110 — so the data is reusable directly. The
engine code that *uses* it is not in any pk3 and would have to be rewritten.

## The Switch Game menu on the PC branch

VRaze's menudef documents its own contract, and their comments name the code:

- `BuildVRGameSelectMenu()` and `BuildVRModSelectMenu()` in `vr_gameselect.cpp`
  insert items into `VRGameSelectMenu` / `VRModSelectMenu` at runtime
- each item fires CCMD `vrselectgame <index>`, handled in `razemenu.cpp`
- game select shows on first startup when multiple games are installed; mod
  select after it, when `raze/mods/` is non-empty
- reachable in-game as `"Switch Game", "g", "VRGameSelectMenu"` — added to
  **eight** menus: `MainMenu` and `IngameMenu` for each of Duke, Blood, SW and
  Exhumed

The menu shell is 25 lines of menudef. The work is the C++ that fills it, and
the mechanism underneath.

### How they switch, and what PC changes

VRaze rewrites `commandline.txt` and restarts the app:

```
VRaze:   raze -gamegrp DUKE3D.GRP #vraze-selected
RazeXR:  raze -gamegrp raze/duke/DUKE3D.GRP
```

**The brief hoped PC might reload a gamegrp in place. It almost certainly
cannot.** `GameMain()` calls `RunGame()` exactly once, inside a try/catch; there
is no re-entry path. The file system, the tile store, the ZScript VM and
`GameStartupInfo` are all global state initialised during that single call.
GZDoom has never supported switching IWAD without a process restart and Raze
inherits that. Making it work would be engine surgery well beyond a feature
branch.

The good news is that PC does not need the Android hack either. Relaunching
`raze.exe` with new arguments and exiting is a few lines and is genuinely
robust — no `commandline.txt`, no marker comment. The open question is what a
relaunch *feels* like in the headset: the OpenXR session tears down, Virtual
Desktop drops you to its environment for a second or two, and the game comes
back. That is a headset question, not a code question, and worth judging once
there is something to judge.

Enumerating the installed games needs no new code — Raze already scans and
CRC-matches every GRP against `grpinfo.txt` during startup, which is what
`grpcrccache.txt` in the VRaze folder caches. That install has 14 GRPs matched
across 8 games.

## Build tooling on this machine

| | |
|---|---|
| MSVC | Build Tools 2019 (14.29) **and** 2026 (14.51) |
| CMake | 3.20 bundled with 2019; **4.3.1** bundled with 2026 |
| git | 2.52.0 |

Raze's `CMakeLists.txt` declares `cmake_minimum_required(VERSION 3.1.0)`.
**CMake 4 removed compatibility with < 3.5 and will hard-error.** Use the VS2019
toolchain — 14.29 is also the closer match to a March 2023 codebase, which
matters given how much of the last two ports was modern-compiler fallout on old
code. Expect to grep the first successful build for warnings regardless;
`shoot_d_override` alone should produce maybe-uninitialised warnings across its
five per-game copies.

`CMakeLists.txt` is **untouched** by the fork — their Android build uses
`android/Android_src.mk`. So the desktop build has never seen the VR layer, and
wiring `RazeXR/*.cpp` plus the OpenXR loader into CMake is new work, not a port.

## Decisions

**Stereo path: two-pass on PC.** Decided by the owner, 2026-08-25. Restore
`vrmi_openxr` to two eyes, define `gl_ViewID_OVR` as 0 on desktop so `main.vp`
compiles unchanged, and write the current eye's projection into slot 0 each
pass. `TBXR_prepareEyeBuffer(eye)` then moves from `FirstEye()` to the per-eye
path.

Rejected: multiview on desktop GL. It would need `GL_OVR_multiview2` on the
driver, 2-layer array swapchains from VDXR, `glFramebufferTextureMultiviewOVR`,
and Raze's postprocess chain made to work on array textures — which they
themselves partly bypassed on mobile (`BlitSceneToTexture` is `#ifndef
__MOBILE__`). The player sees the same image either way; multiview exists to
save mobile CPU/GPU that a PC has spare.

**This is a divergence and is recorded as one.** It is a rendering-path
difference, not a visual one, and belongs in the divergence log alongside any
reproduced defects — not quietly absorbed into "1:1".

## Open

**Voxel weapons.** Whether the PC branch chases VRaze's weapon models as well as
its switcher. Not blocking — the PC branch comes after the 1:1 tag.

No code written yet.

# Milestone 1 (build) — in progress

## Stock Raze builds clean on Windows

The base commit `1147030b`, unmodified, configures and builds with the VS2019
toolchain: `raze.exe`, 9.8 MB, **zero errors and two warnings** — both C4267 in
the vendored `libtess`. Raze is a far better-maintained codebase than
DarkPlaces was, so the "read every warning" lesson will pay off on *their*
changes rather than on the base.

Use the **VS2019** toolchain. Raze declares `cmake_minimum_required(VERSION
3.1.0)` and the CMake 4.3.1 bundled with VS2026 hard-errors on it.

Build the OpenXR loader once (it is a binary, so it is not committed):

```bash
cmake -S <OpenXR-SDK> -B <build> -G "Visual Studio 16 2019" -A x64 -DDYNAMIC_LOADER=ON
```

then point `OPENXR_LOADER_DIR` at the result. `../RazeXR-refs/openxr-build/src/loader/Release`
is the default.

## Android assumptions found so far

Each was a hard build stop, each is one line, and each is the same shape: they

| file | what |
|---|---|
| `gl_load/gl_system.h` | `#include "gl_load/gl_load.h"` replaced by `"android_gl_load.h"` |
| `gl/gl_buffers.h`, `gl_buffers.cpp` | same swap again |
| `gles/gles_renderstate.cpp` | their `mProjectionMatrix[2]` and the new `Set2D(F2DDrawer*)` signature never reached the GLES backend, which they do not compile. Dead code for us too, but it is in the build |

## Divergences — deliberate, and not to be confused with 1:1

1. **Two-pass instead of multiview.** Decided above. `ovrRenderer` regains
   `FrameBuffer[2]`; each eye renders its own pass into its own swapchain.
2. **Haptics.** Theirs plays authored patterns through a Java service, addressed
   by name (`fire_pistol` and so on). There is no PC equivalent of that service,
   so a named event becomes a plain controller pulse through the OpenXR haptic
   action. The events fire in the same places with the same intensities; the
   texture of the pattern is lost. Worth judging in the headset.
3. **Startup order.** Their `AppThreadFunction` does everything before calling
   `raze_main`, because EGL already made the GL context. On PC the context is
   Raze's own and does not exist until the engine opens its window, so the
   sequence splits into `RazeXR_PC_PreInit` (instance, system, eye resolution)
   and `RazeXR_PC_StartVR` (session, renderer, actions).

## Their design, reproduced rather than fixed

Caught while porting, all confirmed against their `TBXR_Common.cpp`:

- **The frustum is the union of the two eyes**, not per-eye asymmetric: the left
  eye's `angleLeft`, the right eye's `angleRight`, and the first eye's up and
  down. Both eyes render with it. Each eye therefore draws a wider field than it
  needs, and the composition layer is handed that same union FOV.
- **The composition layer submits the head pose for both views**, not a per-eye
  pose. The eye separation lives in the projection matrix
  (`VREyeInfo::GetStereoProjection` translates by half the IPD). Feed the
  compositor anything else and the world shears.
- Together these should mean the Quake II edge-culling bug does **not** appear
  here, because the frustum is already wider than either eye needs. Untested.
- `fov_x` is computed at the *end* of `TBXR_submitFrame`, so the engine culls
  frame N against frame N−1's FOV, and against 0 on the very first frame.
- **No MSAA and no supersampling.** `SS_MULTIPLIER` 1.0, `sampleCount` 1,
  `Multisamples` 0, refresh 72. The Quake 1 port defaulted to 1.3x with MSAA on;
  that is Quake's answer, not this one's, and taking it would have been a silent
  fidelity change.

## What the PC layer reuses

Of the 21 `TBXR_*` entry points RazeXR needs, the Quake 1 port's `vr_xr.c`
already implemented 16 under the same names; the rest are renames or arrive with
`OpenXrInput.cpp`, which ports verbatim. `TBXR_PC.cpp` is that file adapted —
1,400 lines, of which the engine coupling was only 21 `qgl*` names, six engine
calls and `vec3_t`. The OpenXR half carries over whole because TBXR_Common is
the same framework in both games.

Their `TBXR_Common.h` was converted **in place**, keeping its name and every
struct, field and function name, so `OpenXrInput.cpp`, `VrInputCommon.cpp` and
`VrInputDefault.cpp` compile against it untouched.

## It links

`raze.exe`, 9.82 MB, **0 errors**. The engine, their VR layer and the PC OpenXR
layer all compile and link with the VS2019 toolchain.

That is a build milestone, not a running one. It has never been launched, the
graphics binding is not yet handed to the session, the two startup halves are
not yet called, and the two-pass render work is still outstanding. **Do not
expect it to render in a headset yet.**

Warnings across the VR layer: 74 C4244, 70 C4101, 12 C4305, 4 C4005. Notably
**none** of the dangerous classes - no C4700/4701/4703 uninitialised use, no
C4172 returned local, no C4715 missing return. The trap that cost an hour on
Quake 1 is not present here.

The four C4005 are worth knowing about:

**`EQUAL_EPSILON` is defined twice, with different values.** Their
`RazeXR/mathlib.h` says `0.001f`; Raze's own `common/utility/vectors.h` says
`(1/65536.)`. That is a factor of 65, and whichever header lands last in a
translation unit wins. This collision exists in **their** Android build too - it
is not something the port introduced - so it is left alone and recorded here.
Worth revisiting if anything in `hw_vrmodes.cpp` compares vectors oddly, since
that file pulls in both.
